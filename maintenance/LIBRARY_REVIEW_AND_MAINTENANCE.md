# Library Review and Maintenance

## Purpose
Keep technology recommendations useful without tying the design standard to a fixed stack.

## Review triggers
Review recommendations when:
- a project starts and a library choice is material;
- a dependency is proposed for production use;
- a framework or major version changes;
- security or maintenance concerns arise;
- an API used by the project is deprecated;
- periodic maintenance is scheduled.

## Review criteria
Check official documentation, supported versions, release activity, security advisories, issue health, accessibility, licensing, bundle cost, compatibility, and alternatives.

## Cadence
For this framework-agnostic standard, review the recommended ecosystem at least every six months, and sooner when a material security or compatibility issue appears. Project teams may require a stricter cadence.

## Rules
- Do not automatically upgrade dependencies as part of a design task.
- Do not recommend a package based on popularity alone.
- Record the date and sources for significant recommendations.
- Keep examples clearly labelled as examples, not mandates.
- Update this guide only when evidence justifies a change.
